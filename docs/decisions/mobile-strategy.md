# 모바일 전략 결정 (#46)

> 결정 문서. errornote는 이미 PWA(Service Worker v2 + IndexedDB 오프라인 큐 + iOS 스플래시,
> #25/#26/#34)로 모바일 설치·오프라인을 지원한다. 본 문서는 **네이티브 React Native 앱을
> 추가로 도입할지**를 평가하고, 도입 시 코드 공유·배포 전략을 정한다.

## 현황

- **설치/홈스크린**: PWA manifest + iOS Add-to-Home-Screen(검증 키트 PR #34).
- **오프라인**: `public/sw.js`(정적 캐시) + IndexedDB 작성 큐(재연결 시 자동 동기화).
- **푸시**: Web Push(VAPID) + 카카오 알림. ⚠️ **iOS Safari Web Push는 16.4+의 "홈스크린 설치 PWA"에서만** 동작 — 일반 모바일 Safari 탭에서는 불가.
- **백엔드 준비도**: Supabase(Auth/PG/Realtime) + `/api/*` + LMS Public API(`/api/lms/*`, API 키 인증) + Swagger. 네이티브 클라이언트가 그대로 소비 가능한 형태.

## 옵션 평가

| 옵션 | 코드 재사용 | 네이티브 역량 | 스토어 | 초기 비용 | 유지비 |
|---|---|---|---|---|---|
| **A. PWA-우선 (현행 강화)** | 100% (단일 코드베이스) | 제한적(iOS 푸시·일부 API 제약) | ❌ (설치 배너만) | 최소 | 최소 |
| **B. Capacitor 래퍼** | 높음(웹 자산 래핑) | 중간(네이티브 푸시·스토어 가능, 플러그인) | ✅ | 낮음~중간 | 중간(빌드 파이프라인) |
| **C. Expo / React Native** | 부분(`lib/` 순수 로직만 공유, UI 재작성) | 높음(완전 네이티브) | ✅ | 높음 | 높음(별도 앱·QA·릴리스) |

### 핵심 트레이드오프
- errornote의 화면 다수가 **텍스트 입력·문서형 학습 UI**라 웹 기술로 충분하며, 네이티브 제스처/카메라/백그라운드 처리 의존도가 낮다.
- 네이티브가 실질 이득을 주는 지점은 **(1) iOS 안정적 푸시, (2) 스토어 노출/신뢰, (3) 백그라운드 음성(발음 연습)** 정도로 한정적이다.
- C(RN)는 학습/대시보드 UI를 사실상 재구현해야 하므로 비용 대비 ROI가 가장 불확실하다.

## 결정 (권장)

**A(PWA-우선)를 기본으로 유지하고, 스토어 진입이 필요해지면 B(Capacitor)로 승급한다. C(풀 RN)는 보류.**

근거:
1. PWA가 이미 설치·오프라인·푸시(설치형)를 커버한다 — 사용자 가치의 대부분을 **추가 비용 0**으로 제공 중.
2. 스토어 노출/iOS 푸시가 비즈니스 요구로 확정되면, Capacitor는 **기존 Next.js 웹 자산을 거의 그대로 래핑**해 네이티브 푸시·스토어 배포를 최소 비용으로 얻는다.
3. 풀 RN(C)은 UI 재작성·이중 QA·릴리스 부담이 크고, 현재 화면 특성상 네이티브 우위가 작아 ROI가 낮다. **사용자 피드백으로 "네이티브가 꼭 필요" 신호가 모이기 전까지 보류.**

## 도입 시 전략 (B 또는 C 확정 시)

- **저장소**: 분리 레포(`errornote-mobile`) 권장. 모노레포는 현 단일 Next.js 앱에 RN 툴체인을 끌어들여 빌드 복잡도를 키운다.
- **코드 공유**: 순수 도메인 로직(`lib/analysis.ts`, `lib/fossilization.ts`, `lib/gamification.ts`, `lib/lti.ts` 등 UI/Next 비의존)을 npm 패키지(`@errornote/core`)로 추출해 공유. UI/데이터 패칭은 비공유.
- **인증/데이터**: `@supabase/supabase-js`로 동일 Auth·RLS 사용. 서버 전용 로직은 기존 `/api/*` 호출(모바일 오리진 CORS 허용 필요).
- **배포**: B는 Capacitor + Fastlane(App Store/Play). C는 Expo EAS.
